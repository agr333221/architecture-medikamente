# Задание 1.3. Список данных для защиты и способы защиты

## 1. Способы защиты

| Способ | Что делает | Обратимость | Где применяется |
| --- | --- | --- | --- |
| Шифрование (Encryption) | Данные преобразуются ключом; без ключа нечитаемы | Обратимо при наличии ключа | Хранение (at rest) и передача (in transit) |
| Токенизация / псевдонимизация | Идентификатор заменяется токеном; соответствие хранится отдельно (Vault) | Обратимо только через сервис токенизации | Межсервисный обмен, озеро данных, партнерские API |
| Обфускация / маскирование (Masking) | Часть значения скрывается при показе (+7 *** ***-12-34) | Необратимо для получателя (оригинал хранится) | UI, логи, тестовые среды |
| Обезличивание (Anonymization) | Удаляются прямые и косвенные идентификаторы, обобщение, агрегация, k-anonymity | Необратимо | Аналитические витрины, ML, отчеты |
| Хеширование с солью (HMAC) | Детерминированный псевдоним для сопоставления без раскрытия | Необратимо | Ключи соединения в аналитике |
| Электронная подпись (УКЭП) | Целостность и авторство документа | - | Медицинские документы, договоры, ЭДО |

## 2. Классы конфиденциальности (используются в тегах)

| Класс | Название | Примеры | Базовая защита |
| --- | --- | --- | --- |
| C0 | Public | Прайс-лист, расписание филиалов | Контроль целостности |
| C1 | Internal | Номенклатура ТМЦ, агрегированные отчеты без ПДн | Доступ только сотрудникам |
| C2 | Confidential | ФИО, телефон, email, дата рождения, платежи | Шифрование at rest и in transit, RBAC, маскирование в UI |
| C3 | Restricted | Данные о здоровье, паспорт, СНИЛС, ИНН, кадровые данные, секреты | Шифрование на уровне полей, ABAC, токенизация, аудит каждого доступа |

## 3. Список данных для защиты

| N | Данные | Категория / класс | Шифрование | Обфускация / маскирование | Обезличивание / псевдонимизация |
| --- | --- | --- | --- | --- | --- |
| 1 | ФИО пациента | PII / C2 | At rest (диск + БД), TLS | В UI ресепшена полностью, в логах - маска "И*** П***" | Токен patient_token во всех сервисах кроме Patient Service; удаляется в витринах |
| 2 | Дата рождения | PII / C2 | At rest, TLS | В UI - только возраст, где достаточно | В аналитике - возрастная группа (5 лет) |
| 3 | Телефон | PII / C2 | At rest, TLS | +7 *** ***-12-34 | Не передается в аналитику |
| 4 | Email | PII / C2 | At rest, TLS | i***@m***.ru | Не передается в аналитику |
| 5 | Адрес регистрации | PII / C2 | Шифрование поля | Скрыт по умолчанию | В аналитике - только регион / город |
| 6 | Место работы / учебы | PII / C2 | Шифрование поля | Скрыт | Не собирать без цели (Data Minimization) |
| 7 | Паспорт, полис ДМС/ОМС, СНИЛС | ID / C3 | Шифрование поля (Vault Transit) + сканы в S3 с SSE | Последние 4 цифры | Токенизация; в аналитику не передается |
| 8 | Хронические заболевания, анамнез, жалобы | PHI / C3 | Шифрование поля, ключи по филиалам | Доступ только лечащему врачу | В аналитике - коды МКБ-10 без связи с личностью, агрегаты |
| 9 | Диагнозы, заключения, назначения | PHI / C3 | Шифрование поля + подписанные ЭМД в S3 | Скрыты для немедицинских ролей | Агрегаты по кодам МКБ-10, k >= 5 |
| 10 | Результаты анализов | PHI / C3 | Шифрование, mTLS с лабораторией | В уведомлениях не раскрываются | Партнеру - order_id вместо ФИО; в аналитике - обезличенные значения |
| 11 | Причина обращения при записи | PHI / C3 | Хранить только в EMR | Скрыта для ресепшена | Не передается в CRM и уведомления |
| 12 | Перечень оказанных услуг, связанный с пациентом | PHI (косв.) / C3 | At rest, TLS | В чеке и 1С - обобщенное наименование | В аналитике - по токену или агрегатам |
| 13 | Платежи (сумма, дата, способ) | FIN / C2 | At rest, TLS | - | Псевдонимизация по patient_token |
| 14 | Данные банковских карт | FIN (PCI) / C3 | Не хранятся (платежная страница эквайера) | Маска 4 цифр | Токен карты у эквайера |
| 15 | Согласия на обработку ПДн | PII / C2 | At rest, подпись | - | Хранятся как доказательство; в аналитику - только факт согласия |
| 16 | Кадровые данные сотрудников (паспорт, СНИЛС, ИНН, оклад, реквизиты) | HR, ID / C3 | 1С в клиент-серверном режиме, шифрование диска и бэкапов | Роли в 1С | В аналитике - агрегаты ФОТ без ПДн |
| 17 | Учетные данные, ключи API, сертификаты | SECRET / C3 | Vault, KMS, HSM / токены | Не логируются | - |
| 18 | Журналы аудита | Internal / C2 | At rest, WORM (неизменяемость) | Маскирование ПДн в событиях | - |
| 19 | Данные складского учета (ТМЦ) | Internal / C1 | Шифрование бэкапов | - | Списание по visit_id вместо ФИО |
| 20 | Контакты представителей поставщиков | PII / C2 | At rest | В отчетах скрыты | Не передаются в аналитику |

## 4. Правила по умолчанию (Privacy by Default)

1. Любое новое поле без тега классификации считается C3 Restricted до ручной проверки.
2. Данные C3 не покидают свой домен (EMR, Patient, HR) иначе как в виде токена или агрегата.
3. Внешним партнерам передаются только данные, явно разрешенные контрактом API с тегами C0-C1
   или псевдонимы (order_id, visit_id).
4. Удаление по запросу субъекта: по patient_token находятся все копии через Data Lineage
   (OpenMetadata) и удаляются / обезличиваются во всех слоях; в Vault уничтожается ключ
   (crypto-shredding) для данных, которые физически удалить нельзя (бэкапы).
