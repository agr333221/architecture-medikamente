# Задание 1.3. Механизм тегирования данных

## 1. Цель

Тегирование позволяет автоматически применять политики доступа, защиты, хранения и удаления
на основе классификации данных, а не ручных договоренностей. Это требование финального
состояния: "в системе есть возможность помечать тегами данные, которые необходимо защитить;
релиз проверяется в автоматическом режиме на работу с тегированными данными".

## 2. Схема тегов

Тег - набор пар "ключ:значение", назначаемый колонке таблицы, полю API / события,
объекту в хранилище файлов или набору данных в озере.

| Ключ | Значения | Назначение |
| --- | --- | --- |
| `cls` | `C0`, `C1`, `C2`, `C3` | Класс конфиденциальности (см. 02-data-protection.md) |
| `cat` | `PII`, `PII.CONTACT`, `ID`, `PHI`, `PHI.LAB`, `FIN`, `FIN.CARD`, `HR`, `SECRET` | Категория данных |
| `owner` | `patient`, `emr`, `appointment`, `payment`, `hr`, `lab` | Домен-владелец данных (Data Owner) |
| `purpose` | `treatment`, `appointment`, `billing`, `marketing`, `analytics`, `legal` | Цель обработки (152-ФЗ ст. 5) |
| `basis` | `consent`, `contract`, `law` | Правовое основание обработки |
| `ret` | `1y`, `5y`, `25y`, `until_revoke` | Срок хранения |
| `prot` | `encrypt`, `tokenize`, `mask`, `anonymize`, `sign` | Обязательные способы защиты |
| `share` | `none`, `internal`, `partner` | Можно ли передавать за пределы домена / компании |

Пример для колонки `emr.diagnosis.text`:

```text
cls:C3 cat:PHI owner:emr purpose:treatment basis:consent ret:25y prot:encrypt,mask share:none
```

Пример для поля партнерского API `LabOrder.order_id`:

```text
cls:C1 cat:PSEUDONYM owner:lab purpose:treatment share:partner
```

## 3. Где хранятся теги

| Слой | Носитель тега |
| --- | --- |
| Каталог данных (источник правды) | OpenMetadata (альтернатива - Apache Atlas): теги на уровне колонок, наследование по lineage |
| PostgreSQL | `COMMENT ON COLUMN` / `SECURITY LABEL` + синхронизация из каталога; представления с маскированием |
| ClickHouse | Теги в каталоге -> генерация `ROW POLICY`, ролей и масок колонок |
| API (OpenAPI) | Расширение `x-data-class` у каждого поля схемы |
| События (Kafka) | Схема в Schema Registry с аннотацией классов полей; заголовок сообщения `x-data-class` |
| Файлы (S3 / MinIO) | Object tags `cls`, `cat`, `ret`; имя объекта - UUID без ПДн |
| Логи и метрики | Поля с `cls >= C2` маскируются агентом логирования до отправки |

## 4. Жизненный цикл тегирования

Новое поле / файл -> автоклассификатор -> тег в каталоге (или ручная проверка) ->
генерация политик + проверка релиза в CI + мониторинг по тегам.

1. **Идентификация.** Автоклассификатор (см. Task6) сканирует схемы и выборки данных:
   регулярные выражения (телефон, СНИЛС, паспорт, email), словари (МКБ-10, ФИО),
   ML-модель NER для свободного текста. Новое поле без тега получает `cls:C3` по умолчанию.
2. **Назначение тега.** Результат с высокой уверенностью записывается автоматически,
   остальное - в очередь Data Steward (бизнес-аналитик / офицер по защите данных).
3. **Применение политик.** По тегам генерируются: роли и row/column policies (ClickHouse),
   представления с маскированием (PostgreSQL), правила API Gateway (удаление полей
   `share:none` из ответов партнерам), правила DLP.
4. **Проверка релиза (shift-left).** В CI каждого сервиса:
   - линтер OpenAPI (Spectral) - у каждого поля есть `x-data-class`; в партнерских контрактах
     нет полей `cls:C3` и `share:none`;
   - проверка миграций БД - новая колонка без тега блокирует релиз;
   - проверка логирования - запрещен вывод полей `cls >= C2`;
   - результаты публикуются в VictoriaMetrics (метрика `release_tagged_data_violations`),
     алерт в Alertmanager / мессенджер команды.
5. **Мониторинг и аудит.** События доступа к данным с `cls:C3` пишутся в SIEM с тегами;
   правила корреляции учитывают класс данных (массовое чтение C3, доступ вне смены).
6. **Поддержание.** Ежеквартальный пересмотр тегов, отчет о покрытии (доля
   классифицированных колонок), обновление словарей.

## 5. Связь тегов и мер защиты

| Тег | Автоматическая мера |
| --- | --- |
| `cls:C3` | Шифрование поля ключом домена, ABAC, аудит каждого чтения, запрет выгрузки в Excel |
| `cls:C2` | Шифрование at rest, маскирование в UI и логах, RBAC |
| `cat:PHI` | Доступ только медицинским ролям с лечебной связью с пациентом |
| `cat:FIN.CARD` | Поле запрещено к хранению - CI блокирует релиз |
| `prot:tokenize` | Значение заменяется токеном при выходе из домена |
| `prot:anonymize` | Поле удаляется / обобщается при загрузке в витрины |
| `ret:*` | Задание очистки (retention job) удаляет данные по истечении срока |
| `basis:consent` | При отзыве согласия обработка по цели `purpose` останавливается |
| `share:partner` | Поле разрешено в партнерских API; иначе вырезается шлюзом |
