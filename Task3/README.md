# Задание 3. Оценка Data Encryption at Rest and In Transit

## 1. Классификация данных

### 1.1. Критерии классификации

| Критерий | Значения |
| --- | --- |
| Чувствительность (класс) | C0 Public, C1 Internal, C2 Confidential, C3 Restricted |
| Категория | PII (ПДн), PHI (данные о здоровье - специальная категория, врачебная тайна), ID (документы), FIN (платежные), FIN.CARD (данные карт), HR (кадровые), SECRET (ключи и учетные данные), OPS (служебные) |
| Состояние | At rest (хранение), In transit (передача), In use (обработка) |
| Профиль риска | Вероятность x ущерб: Высокий / Средний / Низкий |
| Правовой режим | 152-ФЗ, 323-ФЗ, 54-ФЗ, PCI DSS, коммерческая тайна |

Профиль риска определяется: ущерб - юридический (штрафы, оборотные штрафы за утечки ПДн),
репутационный (СМИ, отток клиентов), для пациента (раскрытие диагноза); вероятность - число
пользователей с доступом, число мест хранения, наличие внешних каналов передачи.

## 2. Обоснование защиты и инструменты (по образцу задания)

| Данные | В чем необходимость защиты | Инструменты защиты |
| --- | --- | --- |
| K1 Медицинские данные | Специальная категория ПДн (152-ФЗ ст. 10) и врачебная тайна (323-ФЗ ст. 13); утечка - максимальный ущерб пациенту и репутации, требуется высокий уровень защищенности ИСПДн (ПП 1119) | **At rest:** шифрование полей ключами Vault Transit (AES-256-GCM / ГОСТ 34.12 "Кузнечик"), шифрование томов и бэкапов, отдельные ключи по филиалам, crypto-shredding. **In transit:** TLS 1.3 на периметре, mTLS внутри кластера (service mesh), mTLS + OAuth2 с лабораторией. **In use:** ABAC (лечащий врач), маскирование для немедицинских ролей, аудит каждого чтения, DLP, УКЭП на документы |
| K2 Документы | Используются для мошенничества и кражи личности; ID и сканы - самые "дорогие" данные при утечке | Шифрование полей + сканы в S3 с SSE-KMS и тегами; токенизация (в другие домены - только токен); маска последних 4 цифр; доступ только при оформлении договора; аудит |
| K3 Данные карт | PCI DSS; компрометация ведет к прямому финансовому ущербу пациентов | Не хранить и не обрабатывать: платежная страница эквайера, токенизация карт у эквайера; CI-правило блокирует поля `FIN.CARD` |
| K4 Секреты и ключи | Компрометация ключа = компрометация всех зашифрованных данных | Vault / KMS (с перспективой HSM), авто-ротация, короткоживущие динамические секреты для БД, Kubernetes Secrets только через External Secrets / Vault Agent, раздельные ключи по доменам, двойной контроль (Shamir) на распечатывание Vault |
| K5 Кадровые данные | ПДн сотрудников, налоговая и банковская информация, трудовое законодательство | 1С в клиент-серверном режиме на PostgreSQL, шифрование дисков и бэкапов, VDI, роли 1С, ЭДО / ДиректБанк с УКЭП, журнал регистрации 1С в SIEM |
| K6 Контактные ПДн | ПДн по 152-ФЗ; телефоны и email используются для фишинга и спама; база клиентов - коммерческая ценность | Шифрование at rest (диск / TDE), TLS, маскирование в UI и логах, токены в других доменах, RBAC + ABAC по филиалу, согласия на использование контактов |
| K7 Запись | Связь "пациент - врач - услуга" косвенно раскрывает состояние здоровья | В событиях Kafka - только токены, шифрование топиков на диске, mTLS, ABAC (свои записи / свое расписание), причина обращения в EMR, а не в записи |
| K8 Платежи | Финансовая отчетность, налоговые требования, наименование услуг раскрывает диагноз | Шифрование at rest, TLS, обобщенные наименования услуг в чеках и 1С, RBAC (кассир - филиал, бухгалтер - агрегаты), контроль целостности (подпись выгрузок) |
| K9 Согласия | Доказательство законности обработки; подделка или потеря - нарушение 152-ФЗ | Неизменяемое хранение (append-only, версии), подпись (ПЭП / УКЭП), шифрование at rest, бэкапы |
| K10 Логи и аудит | Доказательная база при инцидентах, могут содержать ПДн | Маскирование ПДн до отправки, TLS до SIEM, WORM / неизменяемые индексы, разграничение доступа (только ИБ) |
| K11 Псевдонимизированные данные | Риск реидентификации при соединении с другими источниками | Таблица соответствия токенов - только в L1 / Vault, row / column policies ClickHouse, доступ по заявке, аудит запросов, запрет выгрузок |
| K12 Обезличенные данные | Низкий риск, но возможна реидентификация малых групп | k-anonymity (k >= 5), подавление малых ячеек, контроль публикации отчетов |
| K13 ТМЦ | Коммерческая информация | Шифрование бэкапов, RBAC, TLS |
| K14 Публичные | Важна целостность (подмена цен, адресов) | TLS, контроль изменений, WAF |

## 3. Стратегия шифрования по состояниям

### 3.1. Data at Rest

| Уровень | Механизм | Для каких классов |
| --- | --- | --- |
| Диск / том | LUKS / шифрование СХД, шифрованные PV в Kubernetes | Все (базовый уровень) |
| СУБД | Postgres Pro Enterprise (TDE) или шифрование томов; ClickHouse encrypted disks | K1-K11 |
| Поле (application-level) | Envelope encryption: DEK шифрует поле, KEK в Vault; Vault Transit | K1, K2, K5 |
| Объектное хранилище | MinIO SSE-KMS, ключ на объект, object tags | K1, K2, K5 (сканы, ЭМД) |
| Бэкапы | Шифрование pgBackRest / Velero ключами KMS, хранение в отдельном контуре | Все |
| Ключи | Vault / KMS, ротация KEK раз в год, DEK - по объему / времени | K4 |

### 3.2. Data in Transit

| Канал | Механизм |
| --- | --- |
| Пациент / сотрудник -> портал, приложение | TLS 1.3, HSTS, certificate pinning в мобильном приложении |
| Внутри кластера (сервис -> сервис, сервис -> БД, Kafka) | mTLS (Istio / Linkerd), TLS до PostgreSQL, ClickHouse, Kafka |
| Партнеры (лаборатория, эквайер, SMS-провайдер) | mTLS + OAuth2 client credentials; ГОСТ TLS там, где этого требует партнер или регулятор |
| Банк, ФНС, ОФД | ДиректБанк, операторы ЭДО, УКЭП (КриптоПро) |
| Филиалы <-> ЦОД | Site-to-site VPN (ГОСТ, сертифицированный криптошлюз) |
| Логи и метрики | TLS до Elastic / VictoriaMetrics |

### 3.3. Data in Use

Обработка в памяти защищается не шифрованием, а ограничением доступа и минимизацией:
ABAC, маскирование, токены вместо ПДн, обезличенные данные для аналитики, запрет локальных
выгрузок (DLP), изолированные среды для ML.

## 4. Автоматизированный контроль за данными

| Контроль | Что проверяет | Инструмент | Реакция |
| --- | --- | --- | --- |
| Классификация и покрытие тегами | Каждая колонка / поле / объект имеет тег `cls` | Classification Engine + OpenMetadata | Метрика покрытия, задачи Data Steward |
| Проверка релиза | Нет нетегированных колонок, нет C3 в партнерских API, нет логирования C2-C3, нет полей карт | GitLab CI: Spectral, Semgrep, проверка миграций | Релиз блокируется |
| Policy as code в кластере | Запрет контейнеров без mTLS, без шифрованных PV, секреты не в env | Kyverno / OPA Gatekeeper | Деплой отклоняется |
| Проверка шифрования | Все БД, тома, бакеты и бэкапы зашифрованы, TLS-сертификаты валидны и не истекают | Скрипты-аудиторы + экспортеры в VictoriaMetrics | Алерт |
| Ротация ключей | Возраст ключей и секретов | Vault + метрики | Алерт, авто-ротация |
| Аудит доступа | Массовое чтение C3, доступ без лечебной связи, доступ вне смены, break-glass | SIEM / UEBA (Elastic Security / Wazuh) | Оповещение ИБ, блокировка учетной записи |
| DLP | Отправка ПДн почтой, копирование на USB, печать | InfoWatch / Solar Dozor | Блокировка / инцидент |
| Сроки хранения | Данные с истекшим `ret` | Retention & Erasure Job | Удаление, отчет |
| Data Lineage | Новые копии данных C3 вне разрешенных хранилищ | OpenMetadata + сканер хранилищ | Инцидент Data Governance |
| Сканирование уязвимостей | Образы, зависимости, конфигурации | Trivy, OWASP ZAP | Блокировка релиза при критичных |

Метрики контроля публикуются в VictoriaMetrics, дашборды в Grafana, алерты через vmalert /
Alertmanager команде ИБ и DevOps.
